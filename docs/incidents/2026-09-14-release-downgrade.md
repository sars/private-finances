# 2026-09-14: a release deployed over a newer one

Статус / severity / affected release: closed / low / dcb497b over 5a29a1b.
Вплив на дані та користувачів: жодних змін даних. Протягом ~13 хвилин production
працював на коміті без 19c279c — виправлення порядку міграції тегів у дереві
категорій. Міграція 25 на той час уже була застосована, тому виправлення не мало
що робити; схема лишалась 26, кількість транзакцій 3 911 незмінна, обидва сервіси
активні, у журналах помилок не було.
Початок, detection, recovery (UTC): перемикання на dcb497b; виявлено одразу після
deploy при звірянні `previousRelease` у виводі switch-release.py; відновлено
перемиканням на 864c90d (поточний main, що містить 19c279c).
Докази: `{"event":"deployment_succeeded","release":"dcb497b…","previousRelease":"5a29a1b…"}`,
далі `{"release":"864c90d…","schema":26,"transactions":3911}`.

Причина і чинники: інвентаризація на початку роботи показала db085ab, а інший агент
випустив 5a29a1b, доки тривала підготовка. `deploy/release.sh` перевіряв лише те, що
ціль є в origin/main, і не порівнював її з тим, що справді працює на сервері, тому
старіший коміт пройшов усі gates.

Відновлення та перевірка цілісності: повторний реліз на 864c90d із тією ж
репетицією міграції на відновленій копії (84 мс, схема 26, 3 911 транзакцій,
нуль витрат без категорії, нуль записів на заголовку). Після перемикання: 60
активних refund-зв'язків, 7 таймерів активні, нуль помилок у журналах обох сервісів.

Regression test / PF-ID / PR: OPS-2; guard у `deploy/release.sh` відмовляє, якщо
поточний реліз не є предком цілі, доки не передано `--allow-rollback`. Окремого
автотесту немає: перевірка виконується самим скриптом перед передачею артефакту.

Що змінити, відповідальний, статус: guard додано (виконано). Довший крок —
перенести реліз у GitHub Actions workflow_dispatch, щоб один одночасний deploy
гарантувався сервером, а не домовленістю між агентами: потребує secrets власника,
відкрито.
